# Agile Experimenter Mentality

## Overview

Reach an honest, decision-useful conclusion with the least experimental and engineering effort. Increase precision only when it could change the technical decision, while preserving the checks that make the evidence valid.

## Workflow

1. **Resolve intent** using **Subcommands**, or recognize experiment work with effective Agile Experimenter principles.
2. **Resolve selectors and scope** using [state.md](references/state.md) and the shared [runtime contract](../../references/runtime-injection.md).
3. **Execute an explicit management action** through its shared detail page, within that action's mutation boundary.
4. **For experiment work**, read the applicable definitions and judgment notes, then use **Applying the Mentality** within the existing task's authority.
5. **Report actual effects** for management actions; for experiments, lead with findings, remaining uncertainty, and the next useful action.

If the task does not map cleanly to these steps, use the native planning tool to make a short task-specific plan from the selected principles and existing constraints. Planning must not invent activation, permission, or new experimental gates.

## When to Use

Use for this mentality's catalog and scope management, or selected guidance on experiment design, benchmark preparation, profiling, and interpretation. Its focus is what evidence to obtain and when enough has been obtained. Brooks covers maintainability, Ponytail covers implementation simplification, and Docs Writer covers durable prose.

Routine technical investigation usually needs direction, approximate magnitude, or a useful discriminator between explanations. Explicit publication, release, safety, or precision requirements remain authoritative. Mentioning this mentality does not authorize an experiment, implementation cleanup, or a change to an approved plan.

## Applying the Mentality

Read and retain selected definitions through shared [Definition Retention](../../references/runtime-injection.md#definition-retention). Apply only effective, relevant guidance through [composition](../../references/composition.md); the following pattern creates no extra activation or checklist requirements.

1. State the question, intended claim, and useful resolution in the existing working context (`e1`, `e3`). Reuse existing answers where they remain applicable.
2. Choose the smallest valid next experiment and a lightweight first-evidence checkpoint (`e2`, `e5`). Resolve any conflict with the approved scope before narrowing it.
3. Use the working execution path, perform checks necessary for safety and interpretation, and obtain measurements (`e2`, `e4`).
4. Compare remaining uncertainty with the distinction that matters (`e3`). Stop with a supported answer, make the cheapest material discriminating check, or report bounded inconclusion.
5. Report the finding, retained evidence, limitations, and any useful next action (`e6`). Separate software preparation from experimental results.

Use existing plans, run directories, and reporting conventions. A short note or ordinary progress update can carry the question and checkpoint; this mentality requires no new manifest, schema, scheduler, or report template.

## Catalog Publication

Publish `.imsight-arts/mentality/agile-experimenter-principles.md` using the shared deployment contract. Copy the complete `Concepts`, `Principle Index`, `Experiment Principles`, `Validity and Claim Boundaries`, `Applicability`, and `Provenance` sections of [principles.md](references/principles.md), including all examples and judgment notes.

Include a title, entrance skill name, canonical index, and availability-only statement. Exclude the source workflow, activation state, and skill-control instructions. The catalog must stand alone inside the target project; publication never enables rules or starts experiments.

The original teaching examples and judgment notes are complete in the catalog. No separate source bundle is declared; application and deployment require neither the originating repository nor network access.

## Rationalization Table

| Rationalization | Counter |
| --- | --- |
| "Someone could question this." | Identify whether that objection could materially change the scoped conclusion. |
| "We should build the reusable harness first." | Name its necessary consumer in the next experiment. |
| "One more round would increase confidence." | Explain which decision the extra precision could change. |
| "The full plan requires everything." | Surface the scope conflict early and propose a smaller milestone without silently dropping requirements. |
| "Every prerequisite is individually useful." | Identify how the next prerequisite enables evidence or protects its validity. |

## Red Flags

- Another abstraction or validator appears before any measured result.
- The workload matrix grows without a question that requires the added subjects.
- The first-evidence checkpoint repeatedly moves while preparation continues.
- Status reports count tests and artifacts but leave the experimental question unanswered.
- A resolved limitation becomes a blocker again without new decision-relevant evidence.

## Guardrails

- DO NOT trade correct work accounting, meaningful controls, or resource safety for a faster-looking result.
- DO NOT treat a noisy unresolved difference as equivalence or claim full parity from a limited diagnostic.
- DO NOT silently weaken explicit scope, precision, validation, or experiment requirements.
- DO NOT continue preparation or sampling solely to defend against hypothetical objections with no material effect on the conclusion.
- DO NOT treat this mentality's activation as authorization for unrelated experiments or infrastructure edits.
- DO NOT apply unselected principles or let this child's guidance override the parent's scope and memory rules.
