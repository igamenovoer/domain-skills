# Report Synthesis

## Workflow

1. Select the report shape appropriate to the request.
2. Group findings by user-relevant questions and separate facts from interpretation.
3. Reconcile conflicts, dates, uncertainty, and source quality.
4. Apply the relevant common-output guidance.
5. Run every check in **Quality Bar** before finalizing.

If the task does not map cleanly to these steps, plan only from the existing report shapes, synthesis rules, source evidence, and quality checks; preserve uncertainty rather than filling gaps.

## Imsight Report Shape

Default report structure:

1. Executive answer: the conclusion in 3-7 bullets.
2. Evidence map: what source classes were consulted and which were strongest.
3. Findings: synthesized themes, not one paragraph per source.
4. Differences and uncertainty: contradictions, stale data, missing primary sources, or assumptions.
5. Recommendation or next actions when the user asked for a decision.
6. Sources: links with short labels and dates when useful.

Adjust the shape to the user request. A quick answer may only need conclusion plus sources; a deep report may need sections, tables, and appendices.

## Synthesis Rules

- Group by user-relevant questions, not by search order.
- Separate facts from interpretation.
- Make tradeoffs explicit when comparing options.
- Prefer tables for comparisons with repeated criteria.
- Use timelines for event sequences and version changes.
- Use a source matrix when claims depend on several sources.
- Avoid dumping raw excerpts. Summarize, then cite.

## Quality Bar

Before finalizing:

1. Check that every major claim has a source or is clearly marked as inference.
2. Check dates for current facts and mention stale sources.
3. Check whether a primary source exists for each important organization-owned claim.
4. Remove weak sources that do not contribute unique evidence.
5. Include links in the final response or in the generated report file.

## Common Outputs

For a market or landscape report:

- Define the category and scope.
- Segment actors by role, buyer, deployment model, or technical approach.
- Identify recent changes with dates.
- End with risks, open questions, and recommended next searches.

For a technical/library report:

- Start from official docs, source repos, release notes, and standards.
- Include supported versions and breaking changes.
- Distinguish documented behavior from examples, issues, or community practice.

For a download/source pack:

- Include a manifest with filenames, source URLs, access dates, and purpose.
- Note skipped sources and why they were excluded.
- Keep raw files separate from processed notes.
